Problem

Browser automation is easy to start and hard to make safe.

A long media batch must survive interruption, respect pacing, prove that captions landed, and stop when the platform signals a restriction. Retrying blindly can duplicate posts or compound an account block.

The design moves sequencing and resume state into a pure core. Volatile Instagram selectors live behind one adapter, and the public demo cannot even load that adapter.

Architecture

Pure batch core. Explicit side-effect boundary.

Dependency injection makes the safe path visible: demo and live share orchestration semantics, not capabilities.

manifest.json→validation→batch core→demo adapter
or live CDP adapter→verification→resume state

Manifest

Stable file key, caption, optional location, and crop intent make each item versionable.

Batch core

Owns ordering, stable-key deduplication, spacing, failure stops, events, and completed keys.

Adapters

The mock emits deterministic steps. The live adapter alone imports Playwright and CDP.

Evidence

Demo reports and live state record item outcomes so an interrupted run can resume.

Workflow

Six guarded transitions before the next Reel.

Each transition has a concrete success signal; a failure stops the batch instead of allowing unsafe continuation.

  1. 01ValidateResolve media and stable key.
  2. 02AttachInject the file through CDP.
  3. 03PrepareSet crop, caption, and location.
  4. 04VerifyRead the caption field back.
  5. 05ShareLive adapter only; wait for completion.
  6. 06PersistWrite completed key, then pace.
Caption + location evidence

The Lexical field is read back after keystrokes and a mismatch raises CAPTION_NOT_SET. Optional location matching is best-effort and records locationSet rather than blocking the Reel.

Action-block stop

Restriction copy raises ACTION_BLOCKED; the batch terminates and tells the operator not to retry that day.

Resumable by key

Completed filenames are skipped before adapter execution, preventing accidental repeats after interruption.

Security boundary

Demo and live mode have different dependency graphs.

The offline route does not rely on flags inside a loaded live client; it never imports that client.

Quality and limitations

What is proven — and what remains volatile.

0demo external writes
5offline core tests
3synthetic fixture items
1explicit live boundary
  • Unit tests cover orchestration, report contract, deterministic output, safe imports, and HTML injection sinks.
  • Pages tests cover desktop/mobile layout, keyboard navigation, reduced motion, report parity, console errors, and unexpected external requests.
  • Instagram has no scheduling step in this web flow; live mode posts immediately and must be operator supervised.
  • Selectors and copy are controlled by Instagram and may require maintenance after UI changes.
  • Pacing reduces risk but cannot guarantee that a platform will accept automated activity.
